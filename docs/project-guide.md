# Work in a Mystack project

Your project was generated by `mystack create`. Start with the root README: it lists your database, runtime, email and payments, with setup commands for that configuration. `mystack.json` is a record of creation choices; editing it does not change application source or dependencies.

## Local configuration

Use Bun for application commands. Copy `.env.example` to `.env` and configure the selected database. Run `bun run db:migrate` before `bun run dev`. PostgreSQL variants also include `db:up` for local Docker and `db:seed` for development users. SQLite variants use normal registration and omit PostgreSQL container/seed scripts.

Open `http://localhost:3000`, matching `APP_ORIGIN` and `BETTER_AUTH_URL`. Authentication email is logged in development when provider credentials are absent. Set a verified sender and real credentials for production. Turnstile and GitHub sign-in are enabled when their required environment values are set.

Migration credentials and runtime credentials have different purposes. PostgreSQL's `DATABASE_MIGRATION_URL` is privileged; runtime access uses an app role via `DATABASE_URL` or the `HYPERDRIVE` binding. D1 uses its `DB` binding, Turso Cloud needs its remote URL/token, and local libSQL/Bun SQLite use a file. Keep file databases on persistent storage in production.

## Application structure

| Path | Responsibility |
|---|---|
| `src/routes/` | TanStack Router pages and HTTP endpoints |
| `src/server/` | Thin TanStack Start server functions |
| `src/services/` | Framework-independent business and domain logic |
| `src/middlewares/` | Database, authentication and authorization boundaries |
| `src/db/` | Selected database driver, generated auth schema and platform tables |
| `src/lib/auth.ts`, `src/lib/auth-client.ts` | Better Auth server/client configuration |
| `src/lib/email.tsx`, `src/lib/email-transport.ts` | React Email rendering and selected transport |

| `src/__tests__/`, `e2e/` | Vitest and Playwright checks |
| `drizzle/`, `scripts/` | Migrations and application hygiene scripts |

## Add your product

Put domain logic in `src/services/` and product tables in the hand-maintained platform schema or new schema modules exported by `src/db/schema.ts`. Keep server functions in `src/server/`; state-changing functions use `method: "POST"` and validate input. Route changes require `bun run generate-routes` and committing the generated tree.

PostgreSQL work that respects RLS uses `withRlsUser` / `withRlsService`. SQLite uses `withDatabaseUser` / `withDatabaseService` as database scopes, plus explicit ownership predicates and authenticated/admin middleware; those helpers do not provide RLS. Preserve the authorization checks when adding tables or queries.

Better Auth is an OAuth/OIDC issuer as well as supporting account sign-in. Preserve signed OAuth search parameters, issuer metadata, the consent query and disabled HTTP paths when customizing authentication. Keep `tanstackStartCookies()` last. After plugin or field changes, run `bun run auth:generate`, then `bun run db:generate` and `bun run db:migrate`. Never edit `src/db/auth.schema.ts` by hand.

Payment integrations record a Purchase and expose the purchase-paid extension point. PostgreSQL fulfillment runs database work inside the paid-state transaction; external IO needs a durable row processed afterward. SQLite atomically writes `purchase_delivery` with the paid state. Implement a consumer using `purchase_id` as its idempotency key for product fulfillment. The starter supplies no wallet, subscription or entitlement domain.

Compose Base UI directly and customize the CSS, layouts, typography and motion. See [DESIGN.md](../DESIGN.md). Preserve focus, reduced-motion behavior and SSR hydration. Add locales through Paraglide and keep user-facing pages localized in both messages and URLs; API/webhook routes stay unprefixed.

## Validate and deploy

```sh
bun run check
bun run typecheck
bun run test:unit
bun run build
bun run check:client-bundle
```

PostgreSQL integration suites use `bun run test` and require Docker. Use `bun run test:e2e` for browser checks with an application running on its configured origin. Native Bun SQLite has its own `bun test` database checks in addition to Vitest.

For production, use the root README's instructions for your selected runtime. `bun run deploy` validates production configuration and checks the client bundle. Workers deploy through Wrangler with `.env.prod`; Nitro and Bun build for a host that injects the production environment, then run `bun run start`. Apply migrations against the production database before starting the new server; D1 hosted migrations use `bun run db:migrate:remote`.

Supply real application origins, a new auth secret, database credentials/resource IDs, email credentials and selected webhook signature secrets. Auth registration creates ordinary users; promote the first administrator through an operator-controlled database action, never open registration. For PostgreSQL, after creating the normal user:

```sql
UPDATE "user" SET role = 'admin' WHERE email = 'you@example.com';
```

Use the equivalent SQL through your selected database's administrative tool for SQLite. Each generated application is owned and maintained independently; the CLI is a creation tool, not an upgrade or runtime dependency.
